## 1. 도메인 설명

- **현장**: 제조업 생산 부서. 생산 담당자가 여러 프로젝트(생산 건)의 일정과 부자재 준비를 함께 맡는다.
- **부자재**: 제품에 함께 들어가는 포장재·체결류·라벨 같은 자재. 발주 단위(예: 800개, 1,500개)로만 살 수 있고, 최소 발주수량(MOQ)과 리드타임이 있다. 여러 프로젝트가 같은 부자재를 함께 쓴다.
- **발주 판단**: `필요수량(생산일정 × BOM) − 현재 재고`를 발주 단위로 올리고, `생산시작일 − 리드타임 − 여유 3영업일`에 발주한다. 안전재고는 두지 않는다.
- **정보가 들어오는 길**: 재고와 일정은 엑셀·PDF·한글 문서에도 있지만, **바뀐 내용은 전화·현장 대화·메신저로 먼저 들어온다.** "라벨 두 롤 남았어요", "P2 다음 주 화요일로 당겨졌어요, 수량은 150개로" 같은 말이다.
- **이미 자동화한 부분**: 계산과 일정 역산은 규칙으로 풀리는 문제라서 계산 엔진과 웹 앱으로 만들어 배포했다 ([PRD.md](../PRD.md), 테스트 549개).

## 2. 현재의 문제

### 2.1 지금의 작업 흐름
말로 듣는다 → 메모한다 → 어느 품목·어느 프로젝트 이야기인지 맞춰 본다 → 엑셀이나 앱에 옮겨 적는다 → 발주를 다시 계산한다.

생산 담당자가 실제로 손이 가장 많이 간다고 꼽은 일은 두 가지다.
1. **말로 들은 내용 받아 적기**
2. **계산과 일정 역산** → 이미 웹 앱으로 해결

### 2.2 수치 (기준선)

| 항목 | 현재 값 | 재는 방법 |
|---|---|---|
| 말로 들어오는 재고·일정 변경 건수 | 【측정 필요】 (예: 하루 n건) | 일주일 동안 건수 세기 |
| 1건을 듣고 → 메모 → 입력 → 발주 재계산까지 걸리는 시간 | 【측정 필요】 (예: 5분) | §10 검증에서 5건 이상 잰다 |
| 받아 적거나 옮기다 틀린 비율 (품목·수량·날짜) | 【측정 필요】 | §10 검증에서 같은 녹음으로 잰다 |
| 메모를 나중에 입력하느라 늦어지거나 빠뜨린 건수 | 【측정 필요】 (예: 주 n건) | 최근 한 달 기억 또는 기록 |
| 그 때문에 생긴 긴급 발주·생산 지연 | 【측정 필요】 (예: 분기 n건) | 최근 분기 발주 기록 |

### 2.3 문제의 구조
1. **말은 기록이 남지 않는다.** 그 자리에서 받아 적지 못하면 내용이 사라지거나 바뀐다.
2. **받아 적은 것을 다시 옮겨 적는다.** 메모 → 표 입력 과정에서 품목, 수량, 날짜가 틀린다. 특히 숫자와 단위(박스인지 개인지)가 섞인다.
3. **말하는 사람마다 품목을 다르게 부른다.** "큰 박스", "외박스", "B 포장박스"가 같은 부자재인지 사람이 맞춰야 한다.
4. **입력이 늦으면, 계산이 정확해도 발주가 틀린다.** 웹 앱은 입력된 값만 계산한다.

정리하면, 발주 **계산**은 이미 풀렸고 남은 병목은 **말로 들어온 정보를 계산에 넣을 수 있는 표로 바꾸는 일**이다. 규칙으로는 사람의 말을 알아들을 수 없으므로, 이 지점이 AI가 들어갈 자리다.

## 3. 개선 가설

> 말로 들어온 재고·일정 변경을 **STT가 받아 적고 LLM이 품목·수량·날짜로 정리**해 주면,
> 듣고 입력해서 발주를 다시 계산하기까지의 시간이 【5분】에서 **1분 이내**로 줄고,
> 그렇게 만든 발주 초안은 사람이 정확히 받아 적어 만든 발주 초안과 **90% 이상 같다.**

| # | 하위 가설 | 확인 방법 |
|---|---|---|
| H1 받아 적기 | STT는 조용한 환경의 한국어 업무 발화에서 품목명과 숫자를 대부분 맞게 받아 적는다 | §6 S1 |
| H2 정리 | LLM은 받아 적은 글에서 종류·품목·수량·날짜를 뽑고, 사람마다 다른 품목 호칭을 부자재 목록에 맞춘다. 정규식 규칙보다 정확하다 | §6 S2, §7 비교 |
| H3 발주 판단 | 그 결과로 계산한 발주 초안이 정답 기준 발주 초안과 같다 | §6 S3 |
| H4 시간 | 녹음 → 정리 → 사람 확인이, 받아 적기 → 옮겨 적기보다 빠르다 | §6 S5 |
| H5 안전 | 틀릴 때는 "확인 필요"가 붙어서, 사람이 모르고 지나가는 오류가 없다 | §6 S4 |

**가설이 틀렸다고 판단하는 조건**: 테스트에서 §6의 목표에 못 미치면 가설을 기각한다. 그때는 어떤 발화에서 왜 실패했는지 분석한 내용을 결과로 낸다.

## 4. 대상 사용자

| 사용자 | 하는 일 | 이 PoC에서 얻는 것 |
|---|---|---|
| **생산 담당자** (주 사용자, 작성자 본인) | 전화·현장에서 들은 내용을 받아 적고 발주를 판단 | 받아 적고 옮기는 일이 "확인"으로 바뀐다 |
| 현장 작업자·타 부서 | 재고와 일정 변경을 말로 알린다 | 하던 대로 말하면 된다 |
| 구매 담당자 | 발주 실행 | 변경이 반영된 발주 초안을 바로 받는다 |

**쓰는 장면**: 전화나 현장에서 들은 내용을 그 자리에서 휴대폰에 다시 말해 녹음한다 → 정리된 표를 확인한다 → 바뀐 발주 초안을 본다. 수량 확정과 발주 실행은 사람이 한다.

## 5. PoC 범위

### 5.1 한정
- **품목 3~5종** (가상의 품목명과 수치. 사내 데이터를 쓰지 않는다)
- **발화 종류 2가지**
  - 재고 보고: "라벨 두 롤 남았어요", "나사 박스 세 개 반 있습니다"
  - 생산일정 변경: "P2 다음 주 화요일로 당겨졌어요", "P1 수량 150개로 늘었습니다"
- **한 번에 한 사람이 말한 짧은 녹음** (10~30초)

### 5.2 범위 밖
- 실제 통화 녹음 사용 (다른 사람의 음성은 개인정보라서 쓰지 않는다. 들은 내용을 본인이 다시 말해 녹음한다)
- 여러 사람이 섞여 말하는 회의 녹음, 실시간 통화 인식
- 거래처 선택, 발주서 발송, 발주 자동 실행
- 웹 앱에 음성 기능을 넣는 것 (PoC는 노트북으로 실행하고, 결과만 웹 앱 형식으로 낸다)

### 5.3 파이프라인 (입력 → AI 처리 → 결과)
```
[입력]    음성 녹음 (또는 메신저·메일의 글 → STT를 건너뛴다)
   ↓
[AI ①]   STT: 음성 → 글
   ↓
[AI ②]   LLM: 글 → 정리된 표
          종류(재고 보고 / 일정 변경), 부자재 코드 또는 프로젝트, 수량·단위, 날짜, 근거가 된 원문
          품목은 부자재 목록 안에서만 고르게 하고, 애매하면 "확인 필요"를 붙인다
   ↓
[확인]    사람이 표를 보고 확정한다
   ↓
[계산]    기존 발주 규칙: 생산일정 × BOM − 재고 → 발주 단위·MOQ 올림 → 영업일 역산
   ↓
[출력]    발주 초안: 품목 / 발주일 / 발주수량 / 예상 입고일 / 발주 후 잔여재고
          + 이번 변경으로 달라진 줄 표시
```

### 5.4 과제 안내의 예시와 다르게 가는 점
- **"안전재고 이하면 발주" 규칙은 쓰지 않는다.** 이 현장의 원칙은 안전재고 없이 생산일정에 맞춰 발주하는 것이고, 그 계산은 이미 만들어 검증했다.
- **거래처는 발주 초안에 넣지 않는다.** 현재 데이터에 거래처 정보가 없다.
- **말로 "발주해 달라"는 요청을 그대로 발주로 만들지 않는다.** 말에서 뽑는 것은 재고와 일정이라는 **사실**이고, 발주할지와 수량은 계산이 정한다.

## 6. 성공 기준

판정은 **범위 안 조건으로 녹음한 테스트 발화 30개 이상**으로 한다. 테스트 조건과 목표는 실험 전에 이 문서로 고정한다.

| # | 지표 | 정의 | 목표 (제안) |
|---|---|---|---|
| S1 | 핵심어 인식률 (STT) | 발화 속 품목명·숫자·날짜 표현 중 STT가 맞게 받아 적은 비율 | **90% 이상** |
| S2 | 정리 정확도 (STT + LLM) | 발화 단위로 종류·품목·수량·단위·날짜가 **모두** 정답과 같은 비율 | **85% 이상** |
| S3 | 발주 판단 일치율 | PoC 결과로 계산한 발주 초안(발주 여부, 발주수량, 발주일)이 정답 기준과 같은 비율 | **90% 이상** |
| S4 | 모르고 지나가는 오류 | 정리 결과가 틀렸는데 "확인 필요" 표시도 없었던 발화 | **0건** |
| S5 | 소요 시간 | 같은 녹음을 수작업(듣기 → 메모 → 입력 → 재계산)과 PoC(녹음 → 정리 → 확인)로 각 5건 이상 측정 | **70% 이상 단축** |
| S6 | 재현성 | 다른 사람이 README만 보고 끝까지 실행 (녹음은 공개하지 않으므로, 저장소에 올린 STT 결과 글에서 시작하거나 자기 목소리로 녹음해서 실행) | 1명 이상 성공 |

- **S4를 따로 두는 이유**: 수량이나 품목이 틀린 채 조용히 들어가면 발주가 빠져 생산이 멈춘다. 틀리는 것보다 틀린 줄 모르는 것이 더 위험하다.
- **긴급 발주·생산 지연 건수는 PoC 기간에 잴 수 없다.** 실제 운영을 몇 달 해야 나오는 값이라, PoC에서는 S3과 S4를 대신 본다.

## 7. AI 모델 선정과 비교 계획

모듈에서 실습한 **STT와 텍스트 생성(LLM)** 을 쓴다. 같은 테스트 녹음에 후보를 모두 돌려 비교하고, 결과와 선정 이유를 노트북에 기록한다.

### 7.1 STT
| 후보 | 실험 전 예상 |
|---|---|
| Whisper 작은 모델 | 빠르지만 품목명과 숫자를 자주 틀릴 것 |
| Whisper 중간 모델 | 속도와 정확도의 절충 |
| Whisper 큰 모델 | 가장 정확하지만 느리다. 사용자 PC(RTX 4070, 8GB)에서 돌아가는지 확인 |

- 비교 항목: S1 핵심어 인식률, 글자 오류율, 처리 시간
- 품목명 목록을 힌트로 주었을 때와 주지 않았을 때도 비교한다

### 7.2 글 → 표 정리
| 후보 | 방식 | 실험 전 예상 |
|---|---|---|
| ① 규칙 (정규식 + 품목 사전) | AI 없이 숫자·단위·품목명을 찾는다 | 정해진 표현만 처리한다. **기준선** 역할 |
| ② LLM, 지시만 | 글을 주고 표로 정리하라고 한다 | 다양한 표현을 알아듣지만, 목록에 없는 품목을 지어낼 수 있다 |
| ③ **LLM + 품목 목록 + 정해진 출력 형식** | 부자재 목록과 호칭 예시를 주고, 정해진 칸만 채우게 한다 | **주 후보** |

- 비교 항목: S2 정리 정확도, S4 모르고 지나가는 오류, 처리 시간, 비용
- LLM 모델도 두 가지 이상 비교한다. 비용이 들지 않도록 사용자 PC에서 Ollama로 돌린다 (2026-11-17 결정, [model-comparison.md](model-comparison.md) §1)
- **STT + LLM을 함께 쓰는 이유**: STT만으로는 "두 롤"이 어느 부자재 몇 개인지 알 수 없고, LLM만으로는 음성을 받을 수 없다. 또 STT가 조금 틀린 글("나벨 두 롤")도 LLM이 품목 목록을 보고 바로잡을 수 있는지 확인한다.

| 녹음이 어려울 때 | 음성 합성으로 만든 음성을 쓰고, 실제 음성이 아니라는 한계를 결과에 밝힌다 |

## 9. 예상 실패 조건

테스트의 "범위 밖 조건 10개"로 일부러 녹음해 확인하고, 결과를 실패 사례로 정리한다.

| 조건 | 실패하는 이유 | PoC에서의 대응 |
|---|---|---|
| 현장 소음, 먼 거리 | STT가 품목명·숫자를 놓친다 | 조건별 오류율 기록, 낮은 신뢰도에 "확인 필요" |
| 숫자 표현 | "천오백", "열다섯", "한 박스 반", "이삼십 개" | 숫자 표현 테스트 묶음, 범위를 말하면 "확인 필요" |
| 단위 혼동 | "세 박스"를 3개로 넣는다 | 단위를 따로 뽑고 입수량으로 환산, 단위가 없으면 "확인 필요" |
| 품목 호칭 | 목록에 없는 별칭, 비슷한 이름의 다른 품목 | 품목 목록 안에서만 고르게 하고, 후보가 둘 이상이면 "확인 필요" |
| 말을 고쳐 말함 | "다섯, 아니 세 박스" | 정정 발화 테스트 |
| 한 번에 여러 건 | "나사는 세 박스, 라벨은 두 롤, 그리고 P2는…" | 여러 줄로 나누어 뽑기 |
| 상대적인 날짜·지시 | "다음 주 화요일", "저번이랑 같게" | 기준일을 주고 날짜로 바꾸기, 앞 내용이 필요하면 "확인 필요" |
| LLM이 지어냄 | 말에 없는 수량·품목을 채워 넣는다 | 근거가 된 원문을 함께 내게 하고, 원문에 없으면 버린다 |

**안전장치**: AI는 초안만 만든다. 표와 함께 원문을 보여 주고, 수량 확정과 발주 실행은 사람이 한다.

## 10. 검증 설계 — 기존 방식과 같은 샘플로 비교

같은 테스트 녹음으로 두 방식을 비교한다.

1. **정답**: 녹음 전에 만든 대본과 정답 표.
2. **수작업**: 녹음을 **한 번만** 듣고 평소처럼 메모한 뒤 표에 입력한다. 걸린 시간과 입력한 값을 기록한다. (대본을 쓴 사람은 내용을 알고 있으므로, 가능하면 다른 사람에게 부탁하거나 며칠 뒤에 한다)
3. **PoC**: 같은 녹음을 넣고, 정리된 표를 사람이 확인한다. 걸린 시간과 결과를 기록한다.

| 비교 | 수작업 | PoC |
|---|---|---|
| 정확도 | 받아 적어 입력한 값 vs 정답 | 정리 결과 vs 정답 (S2) |
| 발주 판단 | 수작업 값으로 만든 발주 초안 vs 정답 기준 | PoC 값으로 만든 발주 초안 vs 정답 기준 (S3) |
| 시간 | 듣기 + 메모 + 입력 + 재계산 | 녹음 + 정리 + 확인 (S5) |

- **정량 결과**: 위 표의 수치, 조건별 오류율 (조용함 / 소음 / 숫자 표현 / 정정 / 여러 건)
- **정성 결과**: 원문 → STT 결과 → 정리된 표를 나란히 놓은 예시를 성공 3개, 실패 3개 이상 싣는다
- **실패 사례**: 조건, 원문, 잘못된 결과, 원인(STT 탓인지 LLM 탓인지), 대응을 표로 정리한다. 범위 밖 조건 10개의 결과도 빼지 않고 모두 싣는다
