## 2. STT 비교

녹음 61개(본인 목소리, 휴대폰)를 Whisper 크기별로 받아 적고 대본과 비교했다. 다시 계산: `poc` 폴더에서 `.venv/Scripts/python tools/eval_stt.py`

**핵심어 인식률(S1)**: 대본의 품목·프로젝트 이름, 숫자+단위, "반", 요일 표현 중 받아 적은 글에도 있는 비율. "두 롤"과 "2롤", "스티커"와 "라벨"은 같은 것으로 센다.

| 모델 | S1 — 테스트, 범위 안 (78개) | S1 — 범위 밖 (23개) | 핵심어를 다 맞힌 발화 (범위 안 30) | 글자 오류율 | 발화당 시간 (CPU) |
|---|---|---|---|---|---|
| `base` | 49% | 43% | 8 | 34% | 0.5초 |
| `small` | 67% | 43% | 11 | 28% | 1.5초 |
| `small` + 품목명 힌트 | 83% | 57% | 20 | 20% | 1.8초 |
| `large-v3-turbo` | 79% | 65% | 17 | 22% | 6.2초 |
| **`large-v3-turbo` + 품목명 힌트** | **86%** | **78%** | 19 | 21% | 6.2초 |

- **선정: `large-v3-turbo` + 품목명 힌트.** 개발용 발화에서 핵심어 인식률이 가장 높았다(90%). 테스트에서는 86%로 **목표 90%에 미달**했다.
- **품목명 힌트의 효과가 모델 크기보다 컸다.** `small`은 힌트만으로 67% → 83%가 되어, 힌트 없는 큰 모델(79%)보다 좋았다. 힌트는 "이런 낱말이 나온다"고 Whisper에 미리 알려 주는 글이다(`poc/src/stt.py`의 `build_hint`).
- **속도가 중요하면 `small` + 힌트**가 대안이다. 3.5배 빠르고 범위 안 인식률 차이는 3%p다. 다만 소음·빠른 말 같은 범위 밖 조건에서는 큰 모델이 뚜렷이 낫다(78% 대 57%).
- **주로 틀리는 것**: 품목 이름("나사" → "다사", "라벨" → "타벨", "뽁뽁이" → "퍽퍽이"), 한 글자짜리 숫자와 단위가 붙을 때("네 롤" → "뇌롤", "두 롤" → "2월", "세 롤" → "세로"), 단위 "개"("백십 개" → "백십 킬로", "80개" → "80K").
- **지어낸 말**: 큰 모델은 말이 끝난 뒤 "감사합니다."를 덧붙인 경우가 5번 있었다. 내용에는 영향이 없었다.
- 글자 오류율은 "두"와 "2"를 다른 글자로 세므로 참고용이다.

## 3. 글 → 표 정리 비교

다시 계산: `poc` 폴더에서 `.venv/Scripts/python tools/report.py`

### 3.1 방식

| 방식 | 내용 |
|---|---|
| ① 규칙 (`rules`) | 정규식 + 품목 사전. AI 없음. **기준선** |
| ② LLM, 지시만 (`plain`) | 품목 목록을 글로 주고, 낱개 수량과 날짜까지 LLM이 직접 계산해서 답하게 한다 |
| ③ LLM + 품목 목록 + 정해진 출력 형식 (`structured`) | LLM은 품목·숫자·단위·날짜 표현을 **뽑기만** 한다. 곱셈(2롤 → 2,000장), 날짜 계산, "확인 필요" 판단은 코드가 한다. 근거로 든 말이 글에 없으면 "확인 필요" |
| ③' ③ + 숫자 보완 (`hybrid`) | 개발용 발화에서 LLM이 "천이백"을 1300으로 읽는 것을 보고 추가. 한글 숫자를 미리 아라비아 숫자로 바꿔 주고, LLM이 적은 수가 글에 있는 수인지 확인한다 |

지시문의 예시 문장은 대본에 없는 문장으로 따로 지었다 (테스트 문장이 지시문에 들어가지 않는지 테스트로 검사한다).

### 3.3 읽는 법과 선정

1. **LLM에게 계산을 맡기면 안 된다 (②).** "두 롤"을 2,000장으로 바꾸는 곱셈과 "다음 주 화요일"의 날짜 계산을 자주 틀리고, 틀려도 "확인 필요"를 붙이지 않는다. 30개 중 20~24개가 조용한 오류였다. 이 방식은 쓸 수 없다.
2. **뽑기와 계산을 나누면 크게 나아진다 (③).** 같은 모델인데 20% → 77%(대본 글), 33% → 73%(STT 글)가 되었다.
3. **숫자 보완(③')은 조용한 오류를 줄였다.** 6건 → 2~3건.
4. **규칙과 LLM은 강한 곳이 다르다.**
   - 깨끗한 글에서는 규칙이 낫다(100% 대 90%). 가설 H2("LLM이 규칙보다 정확하다")는 **깨끗한 글에서는 기각**이다. 단, 대본과 규칙을 모두 Claude가 만들어 규칙에 유리한 조건이었다.
   - STT 글에서는 LLM이 낫다(73% 대 63%). STT가 틀린 품목 이름("다사", "타벨", "퍽퍽이", "웹 박스")을 LLM은 목록을 보고 알아보고, 규칙은 모두 사람에게 넘긴다(확인 필요 9건 대 5건).
   - 반대로 조용한 오류는 규칙이 적다(2건 대 3건).
5. **작은 모델(`qwen3.5:0.8b`)은 이 일에 부족하다.** 절반 가까이를 "확인 필요"로 넘기거나 틀렸다.
6. **선정: ③' (`hybrid`, `llama3.1:8b`).** STT 글에서 정확도가 가장 높고 조용한 오류가 LLM 방식 중 가장 적다. 그러나 **S2 73%(목표 85%), S4 3건(목표 0건)으로 성공 기준에 미달**한다. 미달 원인과 실패 사례는 [evaluation.md](evaluation.md)에 적었다.

### 3.4 개발용 발화에서 고친 것 (테스트를 보기 전)

| 발견 | 고친 것 |
|---|---|
| LLM이 "천이백"을 1300, "팔십"을 90으로 읽음 | 한글 숫자를 미리 아라비아 숫자로 바꿔 주고, LLM이 적은 수가 글에 있는지 확인 (③') |
| 규칙이 "라벨이 두 롤"의 조사 "이"를 숫자 2로 읽음 | 글 전체에서 위치로 찾도록 수정 |
| STT가 "발주해 주세요"를 "말조해 주세요"로 적어 규칙이 재고 보고로 반영 | 부탁하는 말투("주세요")면 "확인 필요" |
| STT가 "80개"를 "80K"로 적어 규칙이 수량을 빼고 날짜만 반영 | "수량"을 말했는데 못 읽으면 "확인 필요" |
| STT가 "나 사", "포장 박스"처럼 띄어 씀 | 품목 이름 글자 사이의 빈칸 허용 |
| STT 결과가 빈 글 (1건) | 빈 글은 LLM을 부르지 않고 "확인 필요" |
