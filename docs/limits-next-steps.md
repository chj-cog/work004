## 1. 추가 시도 — 검증을 더 엄격하게, 규칙과 LLM을 함께

[evaluation.md](evaluation.md) §4.1의 조용한 오류 6건을 보고 두 가지를 더 해 봤다.

> **주의: 이 절의 수치는 공정한 측정이 아니다.** 테스트 결과를 본 뒤에 고친 것이라, 같은 테스트로 다시 재면 좋아 보일 수밖에 없다. 방향이 맞는지 보는 용도이고, 성공 기준 판정에는 쓰지 않는다. 제대로 확인하려면 새 발화로 다시 재야 한다.

LLM을 새로 부르지 않고, 저장해 둔 응답에 검사만 다시 적용했다 (`tools/run_extraction.py --method hybrid2|cascade --replay`).

**시도 1 — 더 엄격한 검사 (`hybrid2`)**

| 더한 검사 | 겨냥한 실패 |
|---|---|
| LLM이 적은 단위가 글에 없으면 "확인 필요" | X06 (단위를 지어냄) |
| 품목 이름이 글에 없고, 한 글자쯤 틀린 것도 없으면 "확인 필요" | X05 ("테이프"를 라벨로 맞춤). "다사" → 나사는 통과 |
| "반"을 붙일 수가 글에 없으면 "확인 필요" | T18 ("한 박스 반"을 0.5로) |
| 글에 있는 숫자가 정리 결과에 없으면 "확인 필요" | T25 (수량 130이 빠짐) — 그런데 실제로는 잡지 못했다 (아래) |

**시도 2 — 규칙 먼저, LLM은 그다음 (`cascade`)**: 규칙이 확정한 발화는 규칙 결과를 쓰고, 규칙이 "확인 필요"라고 한 발화만 LLM(`hybrid2`)에 넘긴다. 규칙은 아는 표현에서 정확하고, LLM은 STT 오타에 강하다는 점을 합친 것이다.

**결과 (입력: STT 글, 테스트)**

| 방식 | 범위 안 30: 정리 정확도 | 조용한 오류 | 확인 필요 | 범위 밖 11: 정확도 | 조용한 오류 |
|---|---|---|---|---|---|
| 규칙 | 19/30 | 2건 | 9건 | 9/11 | 0건 |
| LLM `hybrid` (원래 측정값) | 22/30 | 3건 | 5건 | 6/11 | 3건 |
| 시도 1 `hybrid2` | 21/30 | **1건** | 8건 | 8/11 | 1건 |
| 시도 2 `cascade` | **23/30** | 2건 | 5건 | **9/11** | **0건** |

- **조용한 오류는 줄었지만 0이 되지 않았다.** 시도 1에서 남은 것은 T25(수량 빠뜨림)와 X03(고쳐 말하기)이다. T25는 LLM이 130을 엉뚱한 칸에 적었는데, 새 검사는 "LLM이 어딘가에 적은 수"면 쓴 것으로 쳐서 통과시켰다. 검사를 덧대는 방식으로는 구멍이 계속 남는다.
- **검사를 엄격하게 하면 정확도가 내려간다** (22 → 21). 맞게 뽑은 것도 "확인 필요"로 넘기기 때문이다. 안전과 자동화율은 맞바꾸는 관계다.
- **시도 2가 가장 균형이 좋다.** 다만 규칙이 낸 조용한 오류 2건(T17 "스티커 들어오라고 낮장 300장" → 300, T24 "이십 칠 일" → 7일)이 그대로 남는다. 둘 다 STT가 틀리게 적은 글을 규칙이 그럴듯하게 읽은 경우다.
- **배운 것**: 틀린 것을 사후 검사로 잡는 데는 한계가 있다. 조용한 오류를 0으로 만들려면 "확인 필요가 없는 결과는 믿어도 된다"가 아니라 **모든 결과를 사람이 원래 말과 나란히 보고 확정**하는 화면이 필요하다.

## 2. 한계

| 한계 | 영향 |
|---|---|
| 성공 기준 S1~S4 미달 | 지금은 자동 반영에 쓸 수 없다. 사람 확인이 반드시 필요하다 |
| 발화가 지어낸 문장, 한 사람 목소리, 부자재 4종, 테스트 30개 | 실제 성능은 더 낮을 가능성이 크고, 수치의 오차가 크다 |
| 수작업 기준선 없음 | "기존보다 빠르고 정확한가"에 아직 답하지 못한다 |
| Whisper를 CPU로 실행 (발화당 6초) | 그래픽카드용 라이브러리를 설치하면 빨라지지만 확인하지 않았다 |
| 녹음을 공개하지 않음 | 다른 사람은 음성 단계를 같은 녹음으로 재현할 수 없다. 받아 적은 글부터는 재현할 수 있다 |
| 한 발화씩 따로 처리 | "저번에 말한 대로"처럼 앞 내용이 필요한 말은 처리하지 못한다 |
| 재고·일정 두 종류만 | 발주 요청, 입고 예정, 불량 보고 등은 다루지 않는다 |
| 사진으로 재고를 세는 방식 | 쓸 수 있는 사진이 없어 구현하지 못했다 ([problem-definition.md](problem-definition.md) §12) |

## 3. 다음 스텝

우선순위 순.

1. **확인 화면** — 받아 적은 글, 정리 결과, 달라지는 발주를 한 화면에 나란히 보여 주고 사람이 고쳐서 확정하게 한다. 조용한 오류를 막는 유일한 확실한 방법이다. 기존 웹 앱의 재고·일정 입력 화면에 붙인다.
2. **수작업 기준선 측정** — 테스트 녹음을 듣고 받아 적어 입력하는 시간과 오류를 잰다. S5 판정에 필요하다.
3. **실제 발화로 다시 측정** — 실제 업무에서 들은 말을 품목명만 바꿔 20~30개 모으고, 새 테스트로 `hybrid2`와 `cascade`를 공정하게 잰다.
4. **STT 개선** — 품목명 힌트의 효과가 컸으므로 힌트에 단위와 숫자 예시를 더 넣어 본다. 품목 이름을 틀리게 적는 유형("다사", "타벨")을 사전으로 바로잡는 후처리도 후보다.
5. **LLM 개선** — 고쳐 말하기와 수량 빠뜨림을 줄이도록 예시를 보강하고, 한국어에 강한 다른 모델과 비교한다. 같은 발화를 두 번 정리해 결과가 다르면 "확인 필요"로 넘기는 방법도 있다.
6. **글 입력으로 확장** — 메신저·메일의 글을 같은 정리 단계에 넣는다. STT를 거치지 않으므로 대본 글에서의 결과(규칙 100%, LLM 90%)에 가까울 것으로 예상하지만, 실제 메신저 글은 측정하지 않았다.
7. **기존 웹 앱과 연결** — 확정된 정리 결과를 웹 앱의 재고·생산일정에 반영해 체크리스트가 다시 계산되게 한다.
