## 1. 폴더 구조

기존 웹 앱(`src/`, `supabase/`)은 그대로 두고, PoC는 `poc/` 아래에 파이썬으로 따로 둔다. 실행은 Colab에서 한다.

```
docs/
  problem-definition.md      문제 정의서 (제출물)
  poc-plan.md                이 문서
  model-comparison.md        모델 선정 근거와 후보 비교 결과 (제출물)
  evaluation.md              개선 효과 검증 결과, 실패 사례 (제출물)
  limits-next-steps.md       한계와 다음 스텝, 추가 시도 결과 (제출물)
  images/                    README·문서에 넣는 스크린샷
poc/
  README.md                  실행 방법 (Colab에서 끝까지 따라 하기)
  requirements.txt
  notebooks/
    01_stt_comparison.ipynb     Whisper 크기별 비교 (핵심어 인식률, 시간)
    02_extraction_comparison.ipynb  글 → 표 정리: 규칙 / LLM / LLM + 품목 목록 비교
    03_pipeline_demo.ipynb      음성 → 글 → 표 → 발주 초안 (끝까지)
    04_evaluation.ipynb         수작업과 비교, S1~S5 계산, 실패 사례 정리
    05_text_input.ipynb         추가 시도: 메신저·메일 글 입력
  src/
    stt.py                   음성 → 글
    extract_rules.py         규칙 기반 정리 (기준선)
    extract_llm.py           LLM 정리 (품목 목록, 정해진 출력 형식, 근거 원문)
    review.py                "확인 필요" 판단 (목록에 없는 품목, 단위 없음, 근거 없음 등)
    apply.py                 확정된 표 → 재고·생산일정에 반영
    order_plan.py            발주 계산 (기존 규칙을 파이썬으로 옮긴 것)
    pipeline.py              음성 → 발주 초안까지 한 번에
    evaluate.py              S1~S5 지표 계산
  tests/                     order_plan·extract_rules·review·evaluate 테스트
  data/
    items.yaml               부자재 목록: 코드, 이름, 호칭 예시, 단위와 입수량
    scenario/                가상의 BOM, 생산일정, 발주 단위·리드타임
    utterances.csv           발화 대본과 정답 표 (종류, 품목, 수량, 단위, 날짜, 조건)
    audio/dev/, audio/test/  본인이 녹음한 음성
    manual_baseline.csv      수작업 측정 기록 (시간, 입력값)
  outputs/                   실행 결과 (git 제외)
```

- **발주 계산을 파이썬으로 다시 옮기는 이유**: 기존 엔진은 TypeScript라서 Colab 노트북에서 바로 쓸 수 없다. 다른 사람이 노트북 하나로 끝까지 재현하도록 필요한 규칙을 파이썬으로 옮기고, PRD의 예시(§4.1, §6.4, §6.5)로 두 구현이 같은 답을 내는지 테스트한다.
- **LLM 키**: API를 쓰는 경우 키는 저장소에 넣지 않는다. 노트북에서 실행하는 사람이 자기 키를 입력한다. 키 없이도 재현할 수 있게, LLM 응답을 저장해 둔 파일로 뒤 단계(발주 초안, 지표 계산)를 다시 돌릴 수 있게 한다.

## 2. 단계별 작업

담당: **나** = 사용자, **C** = Claude. 녹음이 필요한 단계는 ★.

| # | 단계 | 담당 | 하는 일 | 끝났다는 기준 |
|---|---|---|---|---|
| 0 | 사전 결정 | 나 | 녹음 가능 여부, 모듈에서 쓴 STT·LLM, 기준선 수치, 실제 발화 예시 5~10개, 마감일 | [problem-definition.md](problem-definition.md) §13이 채워짐 |
| 1 | 뼈대와 계산 | C | `poc/` 폴더, `order_plan.py`, `apply.py`, `evaluate.py`, 테스트. 손으로 만든 표를 넣어 발주 초안까지 실행 | 테스트 통과, PRD 예시와 같은 발주 초안 |
| 2 | 발화 대본과 정답 | C 초안, 나 확인 | 부자재 목록과 호칭, 발화 대본 60개(개발 20 + 테스트 범위 안 30 + 범위 밖 10), 정답 표, 녹음 안내 | `items.yaml`, `utterances.csv`를 사용자가 실제와 비슷한지 확인하고 정답을 확정 |
| 3 | 규칙 기반 정리 | C | 정규식 + 품목 사전으로 글 → 표 (기준선). 대본의 글로 먼저 평가 | 대본 글에서의 정리 정확도 |
| 4 | ★ 녹음 | 나 | 대본 60개를 휴대폰으로 녹음 (범위 밖 10개는 소음·빠른 말 등 조건을 넣어서) | `audio/` 60개 파일 |
| 5 | ★ 수작업 기준선 측정 | 나 (가능하면 다른 사람) | 테스트 녹음을 한 번 듣고 메모 → 입력하는 시간과 값 기록 | `manual_baseline.csv` |
| 6 | ★ STT 비교 | C 작성, 나 실행 | Whisper 크기별, 품목명 힌트 유무 비교 | `model-comparison.md` STT 표 |
| 7 | LLM 정리와 비교 | C 작성, 나 실행 | 지시문 작성(개발용 20개만 보고), 규칙 / LLM / LLM + 품목 목록 비교, LLM 모델 2종 비교 | `model-comparison.md` 정리 표 |
| 8 | ★ 파이프라인 연결 | C | 음성 → 글 → 표 → "확인 필요" → 반영 → 발주 초안, 달라진 줄 표시. 재고 표는 웹 앱 가져오기 형식으로도 저장 | 샘플 녹음 하나로 발주 초안 출력 |
| 9 | ★ 검증 | C 작성, 나 실행 | 테스트 40개로 S1~S5 계산, 조건별 오류율, 성공·실패 예시, STT 탓과 LLM 탓 구분 | `evaluation.md` |
| 10 | 추가 시도: 글 입력 | C | 메신저·메일 글을 같은 정리 단계에 넣기. 음성과 글의 정확도 차이 비교 | `limits-next-steps.md`에 결과 |
| 11 | 문서 마무리 | C | README(실행 방법, 스크린샷), 한계와 다음 스텝, PRD v0.5 연결 절 | 다른 사람이 README만 보고 Colab에서 실행 (S6) |

- 녹음과 Colab 실행은 사용자가 한다. 노트북은 위에서부터 차례로 실행만 하면 되게 만든다.
- 1~3단계는 녹음 없이 진행할 수 있다. 3단계와 7단계는 대본의 글만으로 먼저 평가할 수 있어서, 녹음이 늦어져도 작업이 멈추지 않는다.
- 정답 기록은 사용자가 맡는다. 대본과 정답 초안은 Claude가 만들고, 실제 업무 말투와 맞는지와 정답이 맞는지는 사용자가 확정한다.

## 3. 시간이 부족할 때의 최소 구성

| 반드시 | 줄일 수 있는 것 |
|---|---|
| 1, 2, 4, 7, 8, 9단계 | 발화를 개발 10 + 테스트 30개로 |
| 6단계는 Whisper 두 크기만 비교 | 품목명 힌트 실험 생략 |
| 7단계는 규칙과 LLM + 품목 목록 두 가지만 비교 | LLM 모델 2종 비교 생략 |
| 10단계 대신 "실패 케이스 분석"을 추가 시도로 제출 | 글 입력 확장 |

## 4. 위험과 대응

| 위험 | 대응 |
|---|---|
| 녹음을 할 수 없음 | 음성 합성으로 만든 음성으로 진행하고, 실제 음성이 아니라는 한계를 결과에 밝힌다 |
| 대본을 읽은 녹음은 실제 말투보다 또박또박함 | 대본을 외워서 말하듯 녹음, 범위 밖 조건 10개에 빠른 말·소음·정정을 넣는다. 한계로도 기록 |
| 대본을 쓴 사람이 수작업 측정을 하면 내용을 이미 앎 | 다른 사람에게 부탁하거나 며칠 뒤에 측정. 어려우면 그 사실을 결과에 밝힌다 |
| LLM API 비용·키 | 발화가 짧아 비용은 작다. 키 없이도 저장된 응답으로 뒤 단계를 재현할 수 있게 한다 |
| LLM 결과가 실행할 때마다 달라짐 | 출력 형식을 고정하고, 검증 때의 응답을 파일로 저장해 결과와 함께 올린다 |
| 테스트 발화에 맞춰 지시문을 고치게 됨 | 지시문은 개발용 20개만 보고 다듬고, 테스트 40개는 마지막에 한 번만 돌린다 |
| S2 미달 | 가설 기각으로 정리하고 실패를 STT 탓과 LLM 탓으로 나눠 분석한다 |
